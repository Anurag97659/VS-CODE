The Meeting Place
Cannot Be Changed

A straight road, a handful of friends, and one question: how fast can they all stand on the exact same spot? The answer hides in a trick that shows up constantly in competitive programming — binary search on the answer itself.

binary search ternary search rating ~1600 n ≤ 60,000
01 — The Problem, In Plain Words

What are we actually being asked?

Picture Bytecity's main road as a single straight number line, running south to north. n friends are standing at various points on this line. Each friend i is at coordinate x[i], and can walk north or south at any speed up to their personal maximum v[i] metres per second — they don't have to move at full speed, and they can change direction whenever they like.

Everyone wants to end up standing at the same point at the same moment. That meeting point does not need to be one of the friends' starting positions, and it does not need to be a whole number. We just need to find the smallest possible time at which a common meeting point exists.

Think of it as a rendezvous problem: you get to choose a meeting point and a time, then check whether every friend can physically reach that point by that time without exceeding their speed limit.
02 — The Key Insight

Search over time, not over the meeting point

The tempting first instinct is to search for the place everyone meets. That's messy — the optimal point can be any real number among an infinite set of candidates. Instead, flip the question around and search over time, which behaves far more predictably.

Ask a yes/no question

Fix a candidate time t. For that fixed t, each friend can reach any point inside a closed interval:

// friend i can be anywhere in this range after t seconds
reach(i, t) = [ x[i] - v[i]*t ,  x[i] + v[i]*t ]

All n friends can gather at time t if and only if these n intervals share at least one common point — i.e. their intersection is non-empty. That's a simple, fast, purely numerical check.

Why binary search applies

Here's the property that makes the whole approach work: as t grows, every friend's reachable interval only ever widens (it never shrinks, since speed is fixed and time only increases). Wider intervals are more likely to overlap. That means feasibility is monotonic:

  • If gathering is possible at time t, it is also possible at any time > t — just have everyone stand still for the leftover time.
  • If gathering is impossible at time t, it stays impossible at any time < t.

Because the answer switches cleanly from "no" to "yes" exactly once, binary search can zero in on that switching point — the minimum feasible time — in roughly log₂(range / precision) steps.

03 — The Feasibility Check

Turning "do the intervals overlap?" into two numbers

Checking whether n intervals have a common point doesn't require comparing them pairwise. It only takes two values:

  • maxLow — the largest of all the interval left-ends: max(x[i] - v[i]*t)
  • minHigh — the smallest of all the interval right-ends: min(x[i] + v[i]*t)

The intervals overlap exactly when maxLow ≤ minHigh. If that holds, every point in [maxLow, minHigh] is a valid meeting spot at time t.

function feasible(t, x[], v[], n):
    maxLow  = -infinity
    minHigh = +infinity
    for i in 0..n-1:
        maxLow  = max(maxLow,  x[i] - v[i] * t)
        minHigh = min(minHigh, x[i] + v[i] * t)
    return maxLow <= minHigh

This check runs in O(n) time, which is what makes the whole binary-search wrapper efficient.

07 — Implementation

Putting it together

The full solution is just the feasibility check from Section 03, wrapped in a fixed number of binary-search iterations. Because the answer only needs 10⁻⁶ precision and coordinates go up to 10⁹, around 100 iterations is generously more than enough (each iteration halves the window, so even 60 iterations would already crush the range far past the required precision) — but a common, safe habit is to iterate a fixed ~100 times rather than trying to detect convergence.

C++

#include <bits/stdc++.h>
using namespace std;

int main() {
    int n; cin >> n;
    vector<double> x(n), v(n);
    for (auto &xi : x) cin >> xi;
    for (auto &vi : v) cin >> vi;

    double lo = 0, hi = 1e9; // safe upper bound on the answer
    for (int iter = 0; iter < 100; iter++) {
        double mid = (lo + hi) / 2;
        double maxLow = -1e18, minHigh = 1e18;
        for (int i = 0; i < n; i++) {
            maxLow  = max(maxLow,  x[i] - v[i] * mid);
            minHigh = min(minHigh, x[i] + v[i] * mid);
        }
        if (maxLow <= minHigh) hi = mid;  // feasible -> try smaller t
        else lo = mid;                   // infeasible -> need bigger t
    }
    printf("%.9f\n", (lo + hi) / 2);
}

Python

def feasible(t, x, v):
    max_low  = max(xi - vi * t for xi, vi in zip(x, v))
    min_high = min(xi + vi * t for xi, vi in zip(x, v))
    return max_low <= min_high

n = int(input())
x = list(map(int, input().split()))
v = list(map(int, input().split()))

lo, hi = 0.0, 1e9
for _ in range(100):
    mid = (lo + hi) / 2
    if feasible(mid, x, v):
        hi = mid
    else:
        lo = mid

print(f"{(lo + hi) / 2:.9f}")
08 — Complexity

Why this comfortably fits the limits

  • Per-iteration cost: the feasibility check scans all n friends once → O(n).
  • Number of iterations: fixed, independent of input → O(1) in practice (e.g. 100).
  • Total time: O(n · iterations), which for n = 60,000 and 100 iterations is about 6 million operations — comfortably inside a 5-second limit.
  • Space: O(n) to store positions and speeds.
A common alternative framing you'll see in editorials is ternary search on the meeting point instead of binary search on time — since the maximum time-to-reach-a-point function is convex/unimodal in the point's coordinate. Both approaches are valid; binary-search-on-answer is usually considered the cleaner mental model.
09 — Common Pitfalls

Where people actually lose points

Integer arithmetic. x[i] and v[i] are integers, but t is not — always compute x[i] - v[i]*t in floating point. Mixing integer and float types (or truncating) silently breaks the check.
Too few iterations. Coordinates go up to 10⁹, and the required precision is 10⁻⁶. Stopping binary search after only 20–30 iterations may not be tight enough — 100 iterations is a cheap way to guarantee precision regardless of input scale.
Wrong upper bound for hi. Setting hi too small can clip off the true answer before the search even starts. A generous, easy-to-justify bound like 1e9 (the max coordinate) is safe here since even a stationary friend anywhere on the line is reachable by others within that time.
Confusing "closest pair" with the real check. It's tempting to think only the two most distant friends matter. In general you must fold every friend into the maxLow / minHigh computation — a friend in the middle with a very small speed can be the actual bottleneck.
10 — Recap

The five-line mental model

  1. Reframe the question from "where do they meet?" to "can they meet by time t?"
  2. For a fixed t, each friend's reachable set is an interval [x - vt, x + vt].
  3. All intervals overlap exactly when max(left ends) ≤ min(right ends) — an O(n) check.
  4. Feasibility is monotonic in t, so binary search finds the smallest feasible t.
  5. Run ~100 iterations of binary search to comfortably clear the 10⁻⁶ precision requirement.
